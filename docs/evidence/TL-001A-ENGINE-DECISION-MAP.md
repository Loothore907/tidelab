## One bounded reconnect probe

`scripts/lean_fallback/run_forward_recovery_probe.sh` builds the pinned LEAN source and runs `restore_ledger_partial_reconnect_gap`. The existing managed-feed/`AlgorithmManager` path submits one synthetic order. A mock broker reports and TideLab commits the first of two half-unit fills. Fresh LEAN setup loads an open `PartiallyFilled` order, 0.5 holding, and 9954.955 USD cash. The mock broker then reports the second execution. A small test-owned delivery boundary screens the broker execution ID and exact quantity, price and fee before calling a replaceable engine sink. This case interrupts that sink **after** the test ledger commits the second execution and **before** LEAN receives its event. Reconnect replays the same broker execution ID through the boundary.

The test expects reconnect to suppress the committed ID and detects that the still-running LEAN portfolio remains at the first fill while broker and ledger are at the second fill. It blocks new submissions. A separate fresh setup then reloads the final broker cash and holding. The broker report, execution IDs, interruptions and account are synthetic test doubles. This is a probe of a failure window, not an adapter implementation or a production journal.

Observed in the local runner: `decision=BLOCK reason=engine_behind_broker reconnect=suppressed_committed`; LEAN cash stayed `9954.955` and holding `0.5`, while the broker report and ledger held `9909.91` and `1`. LEAN received zero callbacks and made zero new submissions. A fresh setup loaded the final `Filled` report with zero open orders and zero new submissions. The same runner's prior delivery, forced-exit, partial, conflict and restore cases also ran; the build reported zero errors and upstream package audit warnings. Repository CI does not compile this C# probe.

## Integration comparison and recommendation

LEAN has a public brokerage setup path and a demonstrated managed synthetic feed/manager path, so it is the more promising candidate to continue evaluating. The price is substantial TideLab host work: a broker adapter that retains stable native execution IDs before LEAN `OrderEvent` conversion; durable execution and delivery state; reconnect/revision/correction handling; an in-process account/order reconciliation barrier after a delivery failure; a new-submission hold until broker, ledger and engine agree; and shared H1 strategy and independent risk logic across historical and forward clocks. LEAN's setup restoration alone does not supply that protocol.

NautilusTrader offers compact Python integration and synthetic replay, but the pinned release's external Python data-client plus cache-backing restriction prevents its native backed-recovery result from proving TideLab's replaceable adapter design. Keeping Nautilus would require an evidenced public extension or TideLab-owned persistence/reconciliation path outside that blocked combination. No fork or custom engine is justified by the current record.

**Recommendation:** continue the bounded LEAN evaluation; do not adopt either engine yet. The controlled running-engine interruption and H1 decision-parity cases below passed, but durable correction and multi-order reconciliation remain unresolved. Next prove those through a replaceable adapter and compare its total host work with NautilusTrader's backing gap. Keep [TL-001B issue #3](https://github.com/Loothore907/tidelab/issues/3) independent.
