# TL-002: synthetic H1 report stability across restart

Date: 2026-09-25. Owner: [issue #48](https://github.com/Loothore907/tidelab/issues/48). This uses invented H1 prices, balances, orders and execution IDs on pinned LEAN `88bce0fc6fe282378ee73c54cef1090d0d7a73ee`.

The H1 report bridge now rejects a `.next` candidate left beside the published local report. A process exit between writing that candidate and replacing the report therefore holds reconciliation, revision export, and terminal handoff. The LEAN restore path also refuses the candidate before setup. Once the synthetic candidate is removed, the original complete report restores normally.

For an ordinary restore, the probe compares the same report bytes before reconciliation, after reconciliation, and after LEAN setup. A separate race fixture changes an already recorded partial execution while LEAN calls `GetOpenOrders`. LEAN setup sees the prior cash and holding, but the post-setup comparison detects the changed report and returns `BLOCK_REVISION_RACE`. The SQLite intent remains `submission_unknown`; the corrected execution is rejected by its journal; no new mock `PlaceOrder` occurs. The existing submitted, partial, canceled, terminal-handoff and next-exit paths still pass.

The focused `TL_H1_REPORT_ONLY=1` probe built the pinned runner with 0 errors and 136 existing upstream dependency/toolchain warnings and passed the torn-candidate and mid-setup-correction cases. The bridge remains a test-owned local-file protocol. A stable file before and after setup does not prove an external broker's order/account finality, a broker-atomic snapshot, or immunity to a correction after the final check. A future adapter needs an authoritative consistency token or repeatable snapshot protocol and must hold submissions when that evidence is unavailable. Issue [#3](https://github.com/Loothore907/tidelab/issues/3) separately owns timely forward data; this test used no provider feed, account, or order.
