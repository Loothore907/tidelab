# TL-002 synthetic LEAN intent and account join

Status: bounded [issue #48](https://github.com/Loothore907/tidelab/issues/48) check, 2026-09-24. Uses invented data and the selected LEAN source pin `88bce0fc6fe282378ee73c54cef1090d0d7a73ee`. This is a local mock brokerage probe, not an external broker or an unattended paper service.

The initial LEAN mock `IBrokerage.PlaceOrder` callback now calls TideLab's Python bridge when `TL002_BRIDGE_SCRIPT` is set. The bridge uses the existing `PaperIntentStore` and durably changes the fixed intent to `submission_unknown` before the mock brokerage writes its local order report. A repeated claim fails. In the controlled single-writer fixture, a fresh process can rearm the *same* intent after definitive local absence, while a present order is adopted and held. It never infers absence from LEAN or an external account.

`LeanSyntheticPaperJoin` imports the LEAN mock report into SQLite, binds its LEAN order ID and broker ID to the claimed client ID, and checks ordered report revisions. An append-only execution event table records the invented 0.4-unit fill, then a reversal and replacement for the one-tick correction. Each reconciliation recomputes cash and holding from those events and compares them with the mock broker report. Repeated reconciliation leaves three total events. A changed execution event, changed same-revision report, missing prior order, or wrong cash holds and rolls back the SQLite transaction. Before each fresh LEAN setup in this TL-002 probe, the bridge reconciles this SQLite state; the existing LEAN test also checks its file ledger, restored open order, cash, and holding with zero new submissions.

Run `TL002_JOIN_ONLY=1 bash scripts/lean_fallback/run_forward_recovery_probe.sh <pinned-LEAN-checkout> <dotnet-10-binary>` in WSL/Linux. The runner copies TideLab-authored probe files into the separate pinned checkout and builds its standalone test harness. It uses transient synthetic reports and a transient SQLite database. The LEAN pin check fails if the checkout differs.

This only joins one initial buy and one local corrected partial fill. The next submission remains held in the durable TideLab authority; the older TL-001A next-order probe is separate. The Python bridge is a test harness process boundary, not a production LEAN adapter. No broker atomic snapshot, in-process correction delivery, forward sell, multi-order ledger, realized P&L, arbitrary product rules, crash-safe live adapter, or profitability result follows. TL-001B rights remain a separate gate before real-data strategy work.
