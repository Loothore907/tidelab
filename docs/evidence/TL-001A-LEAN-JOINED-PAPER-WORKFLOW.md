# TL-001A joined synthetic paper workflow and engine-work comparison

Status: issue [#2](https://github.com/Loothore907/tidelab/issues/2), 2026-09-24 Alaska time. Pinned LEAN source `88bce0fc6fe282378ee73c54cef1090d0d7a73ee` is still a candidate, not adopted. This test used invented US-equity prices, a file-backed single-writer mock paper authority, and no market data, account, credential, external broker, live order, or paid service.

## Decisive question and acceptance

Can LEAN submit a paper order through a replaceable brokerage seam, recover a conservatively modeled partial execution and correction after process loss, hold while the execution ledger lags, and submit exactly one next order only after the first order and account reconcile? This addresses the working [selection boundary](TL-001A-CONSERVATIVE-PAPER-FILL.md). The expected negative controls were a missed quote lot, invalid order quantity, missing ledger, stale revision, lagged correction, repeated startup, and incorrect cash report. Any new submission while one of these conditions is unresolved fails the probe.

Run `TL001A_JOINED_ONLY=1 bash scripts/lean_fallback/run_forward_recovery_probe.sh <pinned LEAN checkout> <dotnet 10 binary>`. It builds the TideLab-authored C# probes in the isolated LEAN checkout and runs the phases in fresh processes. Repository CI does not compile or run this C# probe.

## Observed joined sequence

1. A versioned stable client intent is flushed. LEAN's `LimitOrder` passes through its transaction handler to a mock `IBrokerage.PlaceOrder` once; the callback verifies that intent before storing the broker ID and pending account report.
2. The same versioned TideLab cost/fill policy from the [conservative fill checkpoint](TL-001A-CONSERVATIVE-PAPER-FILL.md) sees an invented 89.80/89.90 bid/ask with 0.4 units displayed. It leaves a zero-size quote unfilled and rejects an invalid lot. A one-unit buy produces a **0.4 partial at 89.91**, 0.035964 USD fee, 0.6 remaining, 9964.000036 USD cash and 0.4 holding. The mock authority flushes the execution report, then the process exits before the test ledger write.
3. A fresh process records that stable execution ID once, checks the broker/account arithmetic, and loads one partially filled open order into LEAN. A repeat fresh setup verifies the same execution and makes no new submission.
4. The mock authority revises the execution price to 89.92 and fee to 0.035968 USD. The next-order gate blocks both an older expected revision and the lagging ledger. A fresh process records the correction relationship, loads the corrected 9963.996032 USD cash and 0.4 holding, and still holds the open remainder.
5. The mock authority reports the 0.6 remainder canceled. After LEAN loads zero open orders and the ledger/account agree, TideLab flushes a second stable client intent. LEAN sends one new `LimitOrder` through `IBrokerage.PlaceOrder`; the callback rechecks the report revision, ledger, intent, and first-order closure before storing the second broker ID. Another fresh setup adopts that pending second order without resubmission. A deliberately altered cash report blocks before setup.

The focused runner built with **0 errors** and completed all phases. Its markers included `next=BLOCK_STALE_REVISION or_BLOCK_LEDGER_BEHIND new_submissions=0`, then `decision=SUBMITTED_AFTER_RECONCILIATION new_submissions=1`, and on repeat `decision=ADOPT_EXISTING_NEXT_ORDER open_orders=1 new_submissions=0`. The pinned checkout emitted upstream dependency-audit and SDK warnings. The probe copies TideLab-authored files into that separate checkout; it does not patch LEAN internals.

The new joined harness is about 418 source lines, in addition to the earlier conservative-fill probe and other TL-001A probes. This is **test wiring**, not a measured production adapter estimate. It shows that LEAN's public seams allow the bounded route without copying engine code, while TideLab still owns nontrivial correctness logic. No general order matcher or portfolio engine was added. The work remains inside the agreed *responsibility* boundary, but its maintenance cost needs an explicit design estimate before adoption.

## Limits and decision state

The correction ledger here is an atomically replaced test record with a correction reference, not an append-only production journal. The mock authority is sequential and single-writer; it does not prove cross-process locking, an atomic external broker snapshot, lost-acknowledgement behavior for the second order, or safe concurrent correction at the instant of `PlaceOrder`. The callback rechecks authority state, but the test does not inject a revision race during that callback. Missed/rejected branches exercise the shared policy without driving a complete LEAN broker status transition. The second order remains pending; there is no unattended forward runner or real fill-probability evidence.

**Recommendation:** LEAN remains the stronger initial engine candidate and has passed this specific synthetic joined-route compatibility test. Defer formal adoption while issue #2 records an engine-independent experiment identity/export, a concrete runtime ownership/maintenance estimate, and exact distribution/upgrade obligations; decide whether the remaining paper-source durability and concurrent handoff work belongs in TL-002 under the working selection threshold. Do not start TL-002 solely because this probe passes. TL-001B data rights is separate, and this result offers no evidence that a strategy has positive expectancy.
