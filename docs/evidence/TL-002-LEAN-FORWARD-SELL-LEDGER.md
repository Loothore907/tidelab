# TL-002 synthetic forward sell and two-order ledger

Status: bounded [issue #48](https://github.com/Loothore907/tidelab/issues/48) integration check, 2026-09-24. Uses invented data, the pinned LEAN source `88bce0fc6fe282378ee73c54cef1090d0d7a73ee`, and a single-writer local mock brokerage. It is not an unattended paper service or evidence of real execution or profit.

The first corrected partial buy leaves 0.4 units after its remainder is canceled. The SQLite authority now records a resolution for that buy only when its final order report, three signed fill/correction events, cash `9963.996032`, and holding `0.4` agree. It atomically prepares a second intent for a 0.4-unit sell with a new stable client ID. The mock LEAN `IBrokerage.PlaceOrder` callback must claim that intent durably before writing its sell report. A process exit after the report is followed by a fresh LEAN setup that restores one pending sell, the same cash and holding, and zero new submissions.

The invented broker then reports one sell execution: quantity `-0.4` at `89.79`, fee `0.035916`, cash `9999.876116`, and holding zero. A process exits before the SQLite journal sees it. Reconciliation appends that signed execution once, recomputes account cash and inventory from both orders' four events, and checks the broker report. Fresh LEAN setup restores the flat account with no open order and no new submission. Repeat reconciliation leaves four events. The arithmetic realized result for this invented round trip is `-0.123884`; it is a fixture assertion, not performance evidence.

The first sell attempt did not reach the mock brokerage: LEAN's default equity lot is one unit, so it rejected a 0.4-unit sell while the test had modeled 0.1-unit lots. The passing probe explicitly registers a synthetic 0.1-unit lot and checks that LEAN loaded it. This is a product-capability requirement; real product rules would need a rights-cleared, venue-specific source and a separate adapter.

Run `TL002_JOIN_ONLY=1 bash scripts/lean_fallback/run_forward_recovery_probe.sh <pinned-LEAN-checkout> <dotnet-10-binary>` in WSL/Linux. Python failure checks cover a sell before the buy closes, local absence after claim, conflicting cash, duplicate reconciliation, and a report that disappears after adoption. The runner uses transient synthetic reports and SQLite state; no network market data or private account is used.

This remains a fixed two-order test fixture. The filled sell is not released for a third intent; that requires a general terminal-order and account checkpoint. LEAN order IDs are process-local here, while the broker and client IDs bind the durable order identity. The bridge is a Python subprocess invoked from a LEAN mock callback, with no broker-atomic snapshot, general multi-order runtime, in-process correction delivery, live adapter, or operational monitoring. The selected LEAN build has upstream package audit warnings that require separate dependency and distribution review. TL-001B rights remain separate before real-data strategy work.
